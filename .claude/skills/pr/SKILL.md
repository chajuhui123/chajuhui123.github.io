# pr

이 repo의 PR 템플릿(`.github/PULL_REQUEST_TEMPLATE.md`)과 gitmoji 커밋 컨벤션을
기반으로, 현재 브랜치에 대한 GitHub PR을 생성합니다.

## 절차

1. **안전 체크**
   - `git status --short` — 커밋되지 않은 변경사항이 있으면 멈추고, 먼저
     커밋할지 사용자에게 물어봅니다 (임의로 커밋하거나 버리지 않습니다).
   - `git branch --show-current` — 현재 브랜치가 `main`/`master`면 멈추고,
     어떤 브랜치로 PR을 만들려는 건지 되묻습니다.

2. **diff 범위 파악**
   - base 브랜치를 정합니다 (기본값 `main`, 실제 repo의 기본 브랜치가
     다르면 그걸 따릅니다).
   - `git log <base>..HEAD --oneline` — 마지막 커밋 하나만이 아니라, 이 PR에
     포함될 모든 커밋을 확인합니다.
   - `git diff <base>...HEAD --stat` — 실제로 어떤 파일이 바뀌었는지와
     요약 내용이 맞는지 대조합니다.

3. **템플릿 채우기**
   - `.github/PULL_REQUEST_TEMPLATE.md`를 매번 새로 읽어서 사용합니다
     (시간이 지나며 바뀔 수 있으니 예전 버전을 하드코딩하지 않습니다).
   - **PR 타입**: 이 브랜치의 커밋 로그에 실제로 등장하는 gitmoji에 해당하는
     항목을 전부 체크합니다 (한 브랜치에 ✨/💄/🐛 등이 섞여 있으면 해당하는
     것 전부 체크, 하나만 고르지 않습니다).
   - **개요**: 이 repo의 커밋 메시지처럼 담백하고 "무엇을"보다 "왜"에 초점을
     맞춘 톤으로 2~3줄 작성 — 마지막 커밋만 그대로 옮기지 말고, 범위 안의
     커밋 전체를 종합합니다.
   - **변경 사항**: 커밋을 1:1로 나열하기보다, 의미 있는 변경 단위별로
     묶어서 한 줄씩 정리합니다.
   - **스크린샷 / 데모**: 범위 안에 💄 커밋이나 UI에 영향을 주는 파일
     (`app/**`, `components/**`)이 있을 때만 Before/After 표를 포함한 이
     섹션을 남기고, 그렇지 않으면 섹션 전체를 삭제합니다 — 빈 표를
     남겨두지 않습니다.
   - **체크리스트**: 이번 세션에서 실제로 확인한 항목만 체크합니다 (예:
     `pnpm build`/`tsc`를 직접 돌렸거나, 스크린샷으로 라이트/다크·모바일을
     확인한 경우). 통과할 것 같다는 느낌만으로 체크하지 않습니다 — 검증
     안 된 체크는 솔직한 미체크보다 못합니다.
   - **참고**: 연결할 만한 내용이 없으면 섹션을 삭제합니다.

4. **제목**: 70자 이내로 짧게, 이 PR에서 가장 비중 있는 변경을 대표하는
   gitmoji 하나를 앞에 붙입니다 (`git log --oneline`에 보이는 `✨ ...`,
   `💄 ...` 같은 이 repo의 커밋 스타일과 맞춥니다).

5. **PR 생성**: 브랜치에 upstream이 없거나 원격보다 뒤처져 있다면 먼저
   push(`git push -u origin <branch>`)하고, 작성한 제목+본문을 보여준 뒤
   `gh pr create --base <base> --title "<title>" --body "$(cat <<'EOF'
<채워진 템플릿>
EOF
)"` 형태로 실행합니다.
   - `gh pr view`로 확인했을 때 해당 브랜치에 이미 PR이 있다면 중복
     생성하지 않고, 이미 존재한다고 알린 뒤 본문을 업데이트할지
     (`gh pr edit`) 물어봅니다.

6. 생성된 PR URL을 사용자에게 알려줍니다.
